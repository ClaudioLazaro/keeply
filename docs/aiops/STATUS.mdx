## Resumo de um parágrafo (cole em outro LLM)

Estamos evoluindo o Keep (https://github.com/keephq/keep) para um novo produto AIOps AI-native sem reescrever o núcleo. O Keep permanece o sistema de registro de alertas/incidentes/auth/workflows/providers. O novo plano de controle de IA (monólito modular primeiro) cuida de investigação, agents, RCA, RAG, decisão, policy e execução. O MCP Gateway é o único barramento de ferramentas. A policy é fail-closed; o MVP é suggest-only (sem mutate). Stack de agents: LangGraph para orquestração de investigação, LiteLLM para roteamento multi-modelo, ferramentas apenas via MCP Gateway — não LangChain clássico; CopilotKit fica só na UI. Docs em `docs/aiops/`. Plano adotado; M0 concluído (evento → investigação read-only → writeback na timeline do Keep); próxima fase é o M1. Não fazer fork do Keep. Reusar capacidades existentes; implementar só o que falta.

### Correção de roteamento do frontend (2026-08-01)

A UI estava inutilizável no cluster. **Causa raiz:** os `IngressRoute` dividiam o mesmo host por path entre o Next.js e o keep-api, e os conjuntos de path colidiam. O app em si estava saudável — todas as rotas respondiam 200 dentro do pod.

Três falhas simultâneas:

1. `/` → 307 → `/incidents`, servido pelo **keep-backend** como JSON cru (o rule do frontend listava `/incidents/` com barra final; o do backend usava `PathPrefix('/incidents')` sem)
2. `/backend/*` → 404 no Traefik. É o path relativo que o browser usa (`getApiUrlFromConfig` → default `/backend`), então **todo fetch client-side morria**
3. 10 das 15 seções da UI (`/settings`, `/dashboard`, `/topology`, `/ai`, `/rules`, `/mapping`, `/extraction`, `/maintenance`, `/deduplication`, `/notifications-hub`) davam 404 — não estavam no allowlist enumerado

**Modelo correto (agora em `k8s/06-ingressroutes.yaml`):** o Next.js é dono de todo o path space do host; o browser nunca fala com o keep-api direto (`API_URL` é server-side only e o `middleware.ts` faz o proxy de `/backend/*` in-process). Cada outro serviço ganha um prefixo que não colide:

| Prefixo | Serviço | Middleware |
|---------|---------|------------|
| `/keepapi/*` | keep-backend | `strip-keepapi` + `keep-api-key` |
| `/aiops/*` | aiops-api | `strip-aiops` |
| `/mcp/*` | mcp-gateway | `strip-mcp` |
| `/ws/*` | keep-websocket | `strip-ws` |
| _catch-all_ | keep-frontend | — (priority 1) |

Corrigido junto:

- `PUSHER_HOST` era `keep-websocket` (nome de Service, não resolvível pelo browser) → agora `/ws` relativo, como `usePusher.ts:27` espera; websocket responde `101 Switching Protocols` pelo túnel
- `k8s/05-frontend.yaml` apontava para a imagem publicada `keephq/keep-ui:latest` sem os envs de aiops → agora reflete o cluster: `keep-ui:keeply` (build do `Dockerfile.keeply`), `imagePullPolicy: IfNotPresent`, `AIOPS_API_KEY` do Secret, readiness em `/api/healthcheck`
- `k8s/04-ingress.yaml` (Ingress stock) **removido** — não estava aplicado e suas regras `/api` e `/healthcheck` colidiam com a UI
- Os `IngressRoute` viviam em `/tmp/keeply-ir.yaml`, fora do repo; agora versionados

**Verificado ao vivo pelo túnel:** 15/15 seções da UI em 200 text/html; `/keepapi`, `/aiops`, `/mcp` 200 (catálogo = 19 tools, todas `read`); `/backend/incidents` 200 com Bearer; websocket 101; e2e novo → `rca_ready`, 18/19 tools com evidência (`get_pods` 57 pods + `get_events` 23 events em `backend=live`, gap só em `get_logs`); painel `/api/aiops/*` retorna o RCA draft na página do incidente.

### Correção do redirect para `localhost:3000` (2026-08-01)

Depois do roteamento, a UI ainda jogava o usuário em `http://localhost:3000/`. Causa raiz **no build da imagem**, não no cluster.

Cadeia da falha:

1. `Dockerfile.keeply` / `build-patches.sh` aplicavam um patch forçando `isAuthenticated = true` em NO_AUTH, para "pular o redirect para `/signin`"
2. Mas `/signin` é exatamente onde o provider `NoAuth` (`auth.config.ts:185`) cria a **sessão e o accessToken**
3. Sem sessão, todo fetch client-side para `/backend/*` saía sem `Authorization` → keep-backend respondia **401** (os logs do pod mostravam `Error: No valid session or access token found`)
4. `shared/api/ApiClient.ts:85` chama `signOutClient()` do next-auth em 401
5. O client do Auth.js v5 cai no seu fallback hardcoded `http://localhost:3000/api/auth` — verificado no bundle servido pelo pod

**Correção:** patch removido (`middleware.ts` revertido ao upstream; passo 3 do `build-patches.sh` removido com nota). O fluxo real roda: `/` → `/incidents` → `/signin?callbackUrl=...` → `SignInForm` auto-submete o provider → sessão criada → volta para a app.

Dois bugs de build encontrados no caminho — a imagem em execução tinha sido construída por outro caminho, porque **o `Dockerfile.keeply` não compilava**:

- **`sed` corrompia o `middleware.ts`.** Em replacement de `sed`, `&` sem escape significa "todo o texto casado", então o `&&` do patch de `/api/aiops` duplicava o match e gerava `Expected ')', got 'pathname'`. Corrigido para `\&\&` nos dois arquivos
- **`npm install` pulava as devDependencies.** `ENV NODE_ENV=production` vinha antes do install, e o toolchain de build (`tailwindcss`, `tailwind-variants`, `postcss`, `postcss-import`) mora em devDeps → `Cannot find module 'postcss-import'`. Corrigido com `npm install --include=dev`

Também adicionados `NEXTAUTH_URL` / `AUTH_URL` (build ARG, default `https://keeply.clazar.net`) e `AUTH_TRUST_HOST=true` nos dois estágios. Efeito medido: o `callbackUrl` do redirect agora sai como `https://keeply.clazar.net/...` em vez de `http://`. Nota: isso **não** remove o literal `localhost:3000` do bundle — ele é constante da lib Auth.js; o que resolve o sintoma é o passo 1.

**Verificado ao vivo pelo túnel:** `/` → `/incidents` → `/signin?callbackUrl=https://keeply.clazar.net/incidents` → 200; `POST /api/auth/callback/credentials` emite `__Secure-authjs.session-token` e redireciona para `/incidents`; `/api/auth/session` traz `user=keep`, `tenant=keep`, `accessToken` presente; `/backend/incidents` e `/backend/alerts` em 200 com o token da sessão; zero ocorrências de `No valid session` nos logs; 15/15 seções da UI em 200 text/html; painel aiops devolve o RCA draft.

### Proveniência de evidência + config de agentes (2026-08-01)

Auditoria do fluxo ponta a ponta encontrou um problema de integridade sério: **16 das 19 evidências eram stub (dado fabricado) e nada no sistema sinalizava isso**. A hipótese principal de um RCA real citava `[E11]` = `dd_list_events`, Datadog em modo stub, com 0.70 de confidence. Nem o draft, nem a UI, nem o catálogo distinguiam stub de live. Isso é pior que não ter a feature — é confiança injustificada durante um incidente.

**Proveniência ponta a ponta:**

- Gateway expõe `mode` (stub/live) por tool no catálogo; as 19 anotadas via `mode_setting`
- `evidence.backend` virou coluna indexada (migração 0007). O backfill **não** assume live para linhas antigas — rotular stub como real é exatamente o que a coluna existe para evitar
- Coordinator resolve do resultado da tool, com o catálogo como fallback; ausência conta como `unknown`, nunca `live`
- Draft ganhou linha de proveniência e marca cada bullet stub. Sem nenhuma evidência live: *"No live evidence was collected — this analysis rests entirely on demo data and must not be used to make incident decisions."*
- UI: badge por evidência, banner vermelho/âmbar acima das hipóteses, coluna "Data" em `/aiops/tools`

**Integridade das hipóteses** (`modules/rca/provenance.py`): hipótese sem nenhuma evidência live tem a confidence multiplicada por 0.4 e recebe `⚠️ unverified — stub data only`. Aplicado também ao caminho do **LLM** — o prompt mostra stub e live com o mesmo texto, então o modelo não tem como distinguir. `corroborated`/`caveat` persistidos (migração 0009), senão a API devolveria confidence baixa sem explicação.

**`get_logs` corrigido** — falhava em 100% das investigações. Dois bugs: `_first_pod_name` descartava o namespace (o pod escolhido estava em `cafecafe`, `get_logs` caía no default `"default"`), e escolhia o *primeiro* pod da lista — log de pod saudável é ruído. Agora `_pod_trouble_score` prioriza `waiting` (CrashLoopBackOff) → phase anormal → not-ready → restarts.

| Caps de budget | ConfigMap, exigia restart |
| Severidades que disparam investigação | env |
| Specialists habilitados | não existia |

Credencial **nunca** é armazenada: só o **nome** da env var (`llm_api_key_env`), resolvido do ambiente em tempo de uso. PUT com algo que parece chave (`sk-`, `xox`, `ghp_`, `AKIA`, `Bearer`) → 422. Campos NULL herdam do env, então deployment intocado não muda de comportamento.

<Warning>
**Vazamento encontrado e corrigido durante a validação:** o corpo 422 padrão do FastAPI ecoa o valor submetido no campo `input` — ou seja, rejeitar a chave não bastava, ela voltava ao cliente e iria parar em logs de acesso. `modules/config/errors.py` redige campos com cara de credencial. Verificado no cluster.
</Warning>

**DeepSeek habilitado ao vivo.** Modelos `deepseek-v4-flash` e `deepseek-v4-pro` (confirmados via `/models` da conta — são **modelos de raciocínio**: o `content` só vem após o `reasoning_content`, e ambos consomem o mesmo orçamento de completion; com `max_tokens` baixo o `content` volta vazio e o engine degradaria mudo para o fallback). Adicionado `RCA_MAX_TOKENS = 8000` e erro que nomeia a causa via `finish_reason`.

Testes: 204/204 pytest (13 de proveniência, 24 de config), 40/40 jest (5 suítes).

### Realinhamento: o AI plane parou de ser um sistema paralelo (2026-08-02)

Revisão apontou que a seção AIOps virou **outro sistema dentro do sistema**: integrações que não seguem o padrão de `/providers`, e settings/policies em páginas próprias em vez de `/settings`. A crítica estava certa, e a verificação mostrou que era pior — o Keep tem **126 providers** com catálogo, UI de instalação, secret manager, validação de escopo e rotação, incluindo `datadog`, `argocd`, `eks`, `jira`, `slack`, `kubernetes`, `prometheus`, `deepseek`, `anthropic`, `openai`, `gemini`.

Ou seja: foi construída uma **segunda camada de credenciais** para provedores que o Keep já gerencia — violando o princípio escrito no próprio [overview](/aiops/overview): *"Reusar o que existe; implementar apenas o que falta"*.

**Removido:**

| Removido | Substituído por |
|---|---|
| `modules/config/crypto.py` (envelope Fernet) | secret manager do Keep |
| `agent_config.llm_api_key_encrypted` | provider de IA instalado |
| tabela `config_secret_key` | — |
| tabela `integration_config` | providers instalados |
| dependência `cryptography` | — |
| páginas `/aiops/settings` e `/aiops/policies` | abas em `/settings` |

Migração `0010_drop_parallel_credential_store` (condicional, aplica tanto em bancos que rodaram as revisões retiradas quanto em bancos novos).

**Novo adaptador:** `packages/keep_client/providers.py` lê `GET /providers`, mapeia tipo de provider → integração AIOps e resolve credenciais do secret manager do Keep.

**Mudança conceitual central:** instalar o Datadog em `/providers` é o que liga o specialist de Datadog. Não existe segundo interruptor nem segundo formulário de chave. `mode: live` passou a ser **derivado** de "o provider está instalado".

O que permanece em `agent_config` é só o que o Keep não tem conceito: caps de budget, severidades que disparam investigação e specialists habilitados. `/v1/config/llm-providers` deixou de ser catálogo hardcoded e lista os providers de IA realmente instalados; sem nenhum, a UI aponta para `/providers` em vez de pedir uma chave.

**UI:** `/aiops/integrations` virou read-only (qual provider alimenta quais tools + link de instalação); `AI Agents` e `AI Policies` são abas de `/settings` com deep-link `?selectedTab=`.

228/228 pytest, 58/58 jest.

### IA nativa do Keep habilitada + provider LLM genérico (2026-08-02)

Duas frentes: habilitar as superfícies de IA que já existiam no Keep (que estavam bloqueadas por um flag de env), e tornar o sistema de providers de IA extensível sem código por vendor.

**Superfícies de IA do Keep ligadas.** O flag `OPEN_AI_API_KEY_SET` era puramente env (`OPEN_AI_API_KEY`) e o `/api/copilotkit` instanciava o cliente OpenAI **fixo em `api.openai.com`** — ou seja, mesmo com env setada, uma chave DeepSeek nunca funcionaria. Novo resolvedor `keep-ui/shared/lib/server/getAiProvider.ts`: a credencial vem do **provider de IA instalado no Keep** (o mesmo `/providers` de sempre), com fallback para as envs legadas. Endpoints OpenAI-compatible por tipo (DeepSeek, Gemini, Grok, Anthropic, generic). O flag passa a refletir provider instalado **ou** env — destravando 5 superfícies de uma vez: workflow builder, chat do incidente, resumo do incidente, presets assistidos e teste de step. No `keep-backend`, `OPENAI_API_KEY` + `OPENAI_BASE_URL` no manifesto (o SDK Python honra o base URL — relatórios de incidente também usam o provider).

**Provider genérico OpenAI-compatible** (`keep/providers/openai_compatible_provider/`): `api_url` + `model` + `api_key` opcional. Qualquer vendor OpenAI-shaped — Mistral, Together, Fireworks, Groq, OpenRouter, Azure, vLLM, Ollama, LM Studio, proxy LiteLLM — vira **configuração, não código**. Descoberto automaticamente pelo `providers_factory` (convenção de diretório). Endpoints self-hosted sem credencial usam placeholder key (o SDK exige string não-vazia). `normalizeBaseUrl` no resolvedor completa `/v1` quando o operador cola o host cru.

**`model` configurável na integração.** Os providers de IA eram inconsistentes — só o `anthropic` tinha campo `model`; os outros usavam default hardcoded. Agora `deepseek`, `gemini`, `grok` e `openai` têm campo `model` (opcional) e o `_query` resolve: argumento explícito > modelo da integração > default do vendor. "Qual modelo dentro da integração" é escolha no card do provider, não config em outro lugar.

**Incidente resolvido no caminho:** o `keep-backend` rodava com SQLite **dentro do container** — o PVC `keep-state` estava comentado. Um rollout anterior apagou o banco inteiro do Keep (providers instalados, incidentes, alertas). Corrigido na raiz: PVC habilitado, `/state` montado, `DATABASE_CONNECTION_STRING=sqlite:////state/keep.db`, `strategy: Recreate` (PVC RWO trava rolling update). Verificado: incidente criado sobrevive a restart do pod.

**Verificado ao vivo:** `OPEN_AI_API_KEY_SET: true`; `/workflows/builder` sem o gate; copilotkit responde `CopilotResponse` válido com threadId (sem 503/500); catálogo com `openai_compatible` (125 providers); DeepSeek reinstalado com `model: deepseek-v4-pro`; `/v1/config/llm-providers` reflete `suggested_model: deepseek/deepseek-v4-pro`.

Testes: 9/9 provider genérico (dentro da imagem keep-api), 62/62 jest, 228/228 pytest keep-aiops.

<Note>
**Race de startup observado (não corrigido):** uma investigação anterior tinha 19/19 evidence gaps com `PolicyDenied ... fail-closed deny`. Ela rodou 31s **antes** de `seed_default_policies()` inserir a policy global. O comportamento fail-closed está correto, mas um incidente que chega na janela de cold start do `aiops-api` perde toda a evidência de forma silenciosa. Vale endereçar no M4 (seed via migração, ou readiness gate até a policy existir).
</Note>
